02 · Architecture

Architecture

GET never touches SQLite. Only the writer thread writes the DB and mutates the dict, after COMMIT.
03 · Request flow · Put / Delete

Put: ack only after COMMIT and apply

Delete is the same record type: DELETE FROM kv + dict.pop. Deleting an absent key still goes through a batch, so its 200 means the same thing.

04 · Request flow · Get

Get: a dict lookup, never touches SQLite

Why this is safe

Dict holds only committed values
Queued or uncommitted writes are invisible
No lock: the writer only swaps whole values

Why this is fast

No disk, no writer thread on the read path
Get p99 ≈ 1.2 ms at 1K ops/s
05 · Per-key linearizability

Every key behaves like one copy, in real-time order

single writer threadFIFO write queueapply after commitno application locks
Linearizable = each op appears to take effect at one instant inside its call. Here that instant is the dict apply after COMMIT. No ordering across keys is promised, and none is needed.
06 · Per-key linearizability · scenarios 1/2

Sequential and concurrent operations on one key

ScenarioWhat happensWhy it is correct
Put → 200 → GetReturns that value or a later oneThe 200 is sent only after COMMIT and the dict apply; any Get that starts later reads the updated dict
Delete → 200 → Get404, unless a later Put recreated itSame path: the key is popped from the dict before the 200 is sent
Put ‖ Put on one keyBoth get 200; the one later in the queue winsFIFO drain into one transaction, applied in the same order, so last SQL row = last dict write = last ack. Overlapping ops may be ordered either way
Put ‖ Delete on one keyBoth get 200; the one later in the queue winsDelete is an ordinary record in the batch, not a special case
07 · Per-key linearizability · scenarios 2/2

Overlapping reads, crashes and failed commits

ScenarioWhat happensWhy it is correct
Get during an in-flight PutOld or new value, never torn or uncommittedThe ops overlap, so either order is a valid linearization; the dict swaps whole committed values only
Reads never go backwardsOnce anyone sees v, later reads see v or newerOnly the writer mutates the dict, in queue order, and never rolls back. Visible ⇒ committed ⇒ survives a crash
Acked write, then SIGKILL / restartGet returns the acked value (or a later one)The 200 required a COMMIT with the WAL fsynced. Startup replays the WAL and loads the dict before opening the port. Queued writes are lost, but no client got a 200 for them
COMMIT failsWhole batch → 500, nothing visible, process exitsApply runs only on success. Exiting stops a later batch from committing on top of uncertain disk state; restart reloads the last good commit

Not promised: order across different keys. They may live on different servers and commit independently, which the prompt allows.
