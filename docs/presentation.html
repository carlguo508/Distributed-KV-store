01 · The task

Put / Get / Delete, durable, linearizable per key

Required, all done in v1

  • Per-key linearizability
  • Acked data survives a process restart
  • 1K ops/s · p99 < 50 ms read, < 100 ms write
  • 1–4 servers, start/stop scripts, load generator

Optional, left for next steps

  • Survive losing a server and its disk
  • Failover
  • No stale reads under partition

04 · Phase 2 · Feasibility spike

Measure before picking the stack

My prompt
“Check whether Python can do 1K ops/s with fsync’d writes and still meet p99.”
AI measured
  • os.fsync 0.02 ms vs F_FULLFSYNC 4 ms on macOS
  • Put p99: per-write fsync 56 ms, group commit 11 ms
  • Recommended binary TCP + its own log
My calls
  • Spotted the spike showed writes before fsync → apply after commit
  • Asked for an aiohttp + SQLite prototype instead: 11 / 18 ms → adopted
  • Group commit + fullfsync=ON

08 · Next step 1 · Request de-duplication

The ABA problem: did my timed-out write happen?

Problem

k = A  →  Put B (timeout)  →  k = A
Client cannot tell whether B happened, and a blind retry may write B again.

Idea

Tag each write with a client ID and sequence number. The server remembers what it already applied and answers a retry with the saved result instead of applying it twice.
